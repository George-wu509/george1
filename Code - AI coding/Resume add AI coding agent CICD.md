### 3.4 DevSecOps：2026 年更值得額外強調的能力

這是你原先描述中比較容易忽略的一塊。

特別是 AI Agent 可能會讀取程式碼、執行 Shell Commands、安裝套件，甚至呼叫具有寫入權限的 Tools，因此你應學會：

- Least Privilege：Agent / Workflow 只取得必要權限。
    
- Secret Management：API Keys 不進入 Repository、Prompt 或 Logs。
    
- Dependency Security：偵測 vulnerable packages 和供應鏈風險。
    
- Prompt Injection Defense：將 Repository 內容、Issues、PR Comments 視為可能含惡意指示的資料。
    
- Sandboxing：隔離不可信程式執行，尤其不要讓未審核的 PR Code 直接取得 Cloud Credentials。
    
- Supply Chain Security：管理 Dependency Lockfiles、SBOM、Artifact Provenance 和必要的簽章或 Attestation。
    

這些做法也呼應 GitHub 對工作流程最小權限、Action Dependency 管理和秘密資料保護的安全建議。

### 5.4 一個具體的 AI Coding Workflow 範例

假設你開一個 GitHub Issue：

> Add image quality validation to reject blurry images before AI inference.

你要讓 Coding Agent 完成以下工作：

1. 閱讀 `AGENTS.md` 和現有的 Inference Pipeline。
    
2. 找到影像進入模型前的 Preprocessing 模組。
    
3. 設計 Laplacian Variance 或 Tenengrad Focus Quality Check。
    
4. 實作可以設定 Threshold 的 Quality Validation。
    
5. 新增清晰、模糊、低對比與 Noise 等測試案例。
    
6. 執行 pytest 和 Regression Tests。
    
7. 提交 PR，附上修改摘要、測試結果、已知限制。
    
8. AI Reviewer 檢查例外處理、Threshold、API 相容性與測試覆蓋率。
    
9. CI 驗證通過後，由你審核 Merge。
    
10. 透過 CD 部署到 Staging，執行 E2E，再決定是否發布。
    

這個例子很適合你，因為 Focus Measure、Image Quality、HDR 與 Vision Pipeline 都是你熟悉的技術。你可以把精力集中在 Engineering Automation，而不是重新學習一個完全不熟悉的應用領域。

### 5.5 必須故意測試失敗情境

一個很有說服力的專案，不只是展示 CI 全部綠燈。

我建議至少準備以下測試：

|情境|預期的自動化行為|
|---|---|
|AI Agent 寫出錯誤程式碼|Unit Tests 失敗、PR 不得 Merge|
|修改 API 導致 Backward Compatibility 破壞|Contract / Integration Test 失敗|
|新模型的 Recall 下降|Model Regression Gate 失敗|
|Docker Build 失敗|Release Pipeline 停止|
|Dependency 有已知嚴重漏洞|Security Gate 阻止發布|
|Production Health Check 失敗|停止 Rollout，執行或觸發 Rollback|
|Agent 嘗試讀取未授權的 Secrets|權限拒絕，留下 Audit Record|
|GitHub PR 含惡意 Prompt Injection|Agent 不應執行 PR 文字中的惡意指令|

你可以保存失敗的 PR、CI Logs、Agent Findings 和修復後重新通過的結果，作為 GitHub Portfolio 的證據。

### 5.6 定義可量化的 Quality Gates

以下可以作為初始驗收標準，之後依 Baseline 數據調整：

|指標|建議初始目標|
|---|---|
|Core Module Test Coverage|≥85%|
|Unit / Integration Test Pass Rate|100%|
|Critical Security Findings|0 個未解決|
|Model Numerical Difference|依模型定義誤差容許值|
|Model Accuracy Regression|不低於核准 Baseline 的預設門檻|
|P95 Inference Latency|不超過既定 Performance Budget|
|Release Traceability|每次 Release 可追蹤 Commit、Artifact、Model|
|Rollback Verification|至少成功展示一次可重現的回滾流程|

這些數值是建議的設計目標，不是目前已經達成的專案成果。

另外，CPU-only GitHub-hosted Runner 可以做基本測試；TensorRT / GPU Benchmark 則應該安排在有 GPU 的受控環境執行。不建議讓不可信的外部 PR 在帶有雲端憑證的 GPU Runner 上直接執行。

### 6.3 最重要的部分：建立 Coding Agent Evaluation

這會是整個專案最能凸顯 Senior AI Engineering 能力的部分。

建議建立專屬的 Golden Test Set，包含：

- 具有已知 Bug 的 PR。
    
- 沒有 Bug 的正常 PR。
    
- 缺少必要測試的 PR。
    
- 產生效能退化的 PR。
    
- 包含 Race Condition 或 Resource Leak 的 PR。
    
- 含 Prompt Injection 的惡意 PR。
    
- 要求 Agent 超出權限的 Task。
    

評估指標可以包含：

|指標|定義|
|---|---|
|Bug Detection Recall|已知 Bug 中，有多少被正確發現|
|Review Precision|Agent 報告的問題中，有多少是真實問題|
|False Positives per PR|每個 PR 平均產生多少無效警告|
|Patch Success Rate|產生的 Patch 有多少通過獨立測試|
|Task Completion Rate|Agent 完成指定需求的比例|
|Regression Rate|修正問題後造成其他測試失敗的比例|
|Tool Selection Accuracy|是否選擇正確的工具及參數|
|Security Violation Rate|是否有越權或違反安全規則的行為|
|Cost per Completed Task|每個完成任務的 Token / API 成本|
|P95 Task Latency|95% 任務完成所需時間|

如果你能在 GitHub 展示一組 30–50 個有標記的測試任務，比只展示「Agent 成功修了一個 Bug」更有說服力。

尤其應區分：

Agent 自己產生的測試通過，不等於 Agent 正確完成任務。

需要有獨立的 Hidden Tests、Reference Behavior 或人工標記，避免 Agent 修改測試來掩蓋錯誤。

## 十、最後給你的優先建議
