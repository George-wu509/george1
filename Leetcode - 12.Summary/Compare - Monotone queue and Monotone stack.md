#### 選擇規則與心法 (How to Choose)

1. **先判斷是「區間問題」還是「相對位置問題」**
    - 如果題目有一個**動態移動的框框**（長度固定為 K，或者快慢指針組成的視窗），且你需要知道這個框框內的極值 $\rightarrow$ **單調隊列**
    - 如果題目是問「針對陣列裡的每個數字，找它**左邊或右邊最近**的某個極值邊界」，與視窗無關 $\rightarrow$ **單調棧**。
        
2. **判斷是否需要「回頭處理」**
    - 如果遇到某個符號或條件時，需要**馬上回頭結算**剛剛累積的東西（例如遇到 `)` 要立刻回頭找 `(`，或者遇到 `*` 要立刻拿出前一個數字計算） $\rightarrow$ **一般棧**。
        
3. **判斷是否為「地毯式擴展」**
    - 如果問題是「水波紋般向外擴散」或「從一樓找完才能找二樓」 $\rightarrow$ **一般隊列 (BFS)**。



#### 單調stack跟單調queue是否都有在內部維持單調遞減or單調遞增的概念
```
單調stack跟單調queue是否都有在內部維持單調遞減or單調遞增的概念, 或者單調stack只有 維持單調遞減? 或者是依題目而選擇是用單調stack 維持單調遞減, 單調stack 維持單調遞增, 單調queue 維持單調遞減, 單調queue 維持單調遞增? 我常會搞混是否能用leetcode例題解釋這四種要怎麼選擇? 另外除了單調stack跟單調queue之外還有其他的data structure也會有內部維持單調遞減or單調遞增的概念?
```
單調棧（Monotonic Stack）與單調隊列（Monotonic Queue）**都有**單調遞增與單調遞減的型態，到底要用哪一種，完全取決於題目的物理情境與限制，而不是資料結構本身的死規定。

要精準選擇這四種變體，你只需要問自己兩個問題：

1. **範圍受限嗎？** 如果是「沒有範圍限制，只要找到下一個符合條件的數」，用**單調棧**；如果是「在一個固定大小的滑動窗口（Sliding Window）內找極值」，用**單調隊列**（通常用 Deque 實作）。
    
2. **要找大還是找小？** 找下一個「更大」的數，用**單調遞減**；找下一個「更小」的數，用**單調遞增**。

以下將這四種選擇與 LeetCode 經典題型對應拆解：

## 1. 單調棧：尋找「下一個更大 / 更小」元素

單調棧的核心是不斷壓入元素，直到遇到一個「破壞單調性」的元素，這個破壞者就是我們要找的答案。

|**資料結構型態**|**內部狀態 (底 -> 頂)**|**觸發 Pop 的條件**|**物理意義**|**LeetCode 經典題例**|
|---|---|---|---|---|
|**單調遞減棧**|大 $\rightarrow$ 小|當前元素 **>** 棧頂|尋找**下一個更大**的元素。|**739. Daily Temperatures**<br><br>  <br><br>棧裡存著還沒找到更暖和日子的天數。遇到高溫（當前元素大），就把較冷的日子（棧頂）彈出，計算等待天數。|
|**單調遞增棧**|小 $\rightarrow$ 大|當前元素 **<** 棧頂|尋找**下一個更小**的元素。|**84. Largest Rectangle in Histogram**<br><br>  <br><br>棧裡存著可以繼續往右延伸的長方形。遇到較矮的柱子（破壞遞增），代表前面的長方形遇到邊界，必須彈出並結算面積。|

## 2. 單調隊列：維護「滑動區間」內的極值

單調隊列除了像棧一樣在尾部彈出（剔除永遠不可能成為答案的廢物），還要從頭部彈出（剔除已經滑出窗口的過期元素）。

|**資料結構型態**|**內部狀態 (頭 -> 尾)**|**尾部 Pop 條件**|**物理意義**|**LeetCode 經典題例**|
|---|---|---|---|---|
|**單調遞減隊列**|大 $\rightarrow$ 小|當前元素 **>** 隊尾|維護窗口內的**最大值**（隊列頭部永遠是當前最大）。|**239. Sliding Window Maximum**<br><br>  <br><br>新進來的數字比較大，代表前面比它小的數字在未來的窗口裡「絕對不可能成為最大值」，直接從尾部刪掉。|
|**單調遞增隊列**|小 $\rightarrow$ 大|當前元素 **<** 隊尾|維護窗口內的**最小值**（隊列頭部永遠是當前最小）。|**862. Shortest Subarray with Sum at Least K**<br><br>  <br><br>維護 Prefix Sum 的遞增。如果新的前綴和比較小，代表用它當減數可以得到更大、更短的子陣列，淘汰前面較大的前綴和。|

## 其他具有單調性概念的資料結構

除了 Stack 和 Queue，程式語言中還有其他資料結構在內部設計上依賴單調性：

- **Heap / Priority Queue (優先隊列)**
    
    - **概念**：內部雖然不是完全線性的單調，但在任意一條從根節點到葉節點的路徑上，都維持著**單調遞增（Min-Heap）**或**單調遞減（Max-Heap）**。
        
    - **用途**：不需要理會元素的進場順序或窗口限制，只要隨時能取出「全域」的最大值或最小值（時間複雜度 $O(\log n)$）。
        
- **Binary Search Tree (二元搜尋樹, BST)**
    
    - **概念**：BST 的中序遍歷（Inorder Traversal）天生就會輸出一個**嚴格單調遞增**的數列。
        
    - **用途**：需要動態插入、刪除，並且隨時要查詢某個數字的 Rank（排名）或找尋 Lower Bound / Upper Bound 時使用。
        
- **Fenwick Tree (Binary Indexed Tree) / Segment Tree (線段樹)**
    
    - **概念**：在處理「區間和」或「區間極值」時，這類樹狀結構通常會搭配具備單調性的屬性（例如前綴和陣列本身的單調性）來進行快速的二分搜尋 ($O(\log n)$)。




#### 單調隊列跟單調棧在維護單調性一樣, 那差別在哪
```
我比較使用單調遞減隊列解題的leetcode 滑動窗口最大值, 以及使用Monotonic Stack下一個更大元素的題目. 我發現在使用單調遞減隊列用deque宣告了dq, 以及Monotonic Stack裡面宣告的stack, 都同樣是維持dq or stack裡面的嚴格遞減, 而當進來的下一個數字如果大於dq or stack的最後一個元素, 那就會把這個比較小的元素踢出去用新的替代. 那這時為什麼一個要用Monotonic queue一個要用Monotonic Stack?
```
你的觀察非常精準。在**維護單調性（從尾端踢掉較小元素）**這件事上，兩者的邏輯與程式碼寫法幾乎一模一樣；它們之所以需要不同的資料結構，差別完全在於**「另一端（頭部／底部）的元素會不會過期」**。

|     |                                                                                                                                                                                                                                                         |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
|     | Monotonic queue<br>Q:滑動窗口最大值<br>nums = [1, 3, -1, -3, 5, 3, 6, 7], k=3<br>                   p<br>0:dq =  [1] -> res = []<br>1:dq =  [3] -> res = []<br>2:dq =  [3,-1] -> res = [3]<br>3:dq =  [3,-1,-3] -> res = [3,3]<br>3:dq =  [5] -> res = [3,3,5] |
|     | **單調隊列（Monotonic Queue）必須操作「兩端」**：除了在尾端維持單調遞減，因為題目多了一個**滑動窗口的範圍限制**，躺在最前面的最大值一旦滑出窗口左邊界就必須淘汰，因此需要能從頭部刪除（`pop_front` / `popleft`）的雙端隊列 `deque`                                                                                                            |
|     | Monotonic Stack<br>Q:下一個更大元素的題目<br>nums = [3, 1, 2, 4]<br>                 p<br>0:stack = [3], result= [x,x,x,x]<br>1:stack = [3,1], result= [x,x,x,x]<br>2:stack = [3,2], result= [x,2,x,x]<br>3:stack = [3,4], result= [x,2,x,x]                      |
|     | - **單調棧（Monotonic Stack）只需操作「一端」**：元素進入後，只有「遇到比它大的新元素」這一種死法，永遠不會因為距離太遠而失效，所以用後進先出（LIFO）的 `stack` 就夠了                                                                                                                                                    |

#### 核心機制對比

|**比較維度**|**單調遞減棧（Next Greater Element）**|**單調遞減隊列（Sliding Window Maximum）**|
|---|---|---|
|**操作端點**|**單端**（僅棧頂 `push` / `pop`）|**雙端**（隊尾 `push_back` / `pop_back`，隊頭 `pop_front`）|
|**我們想知道什麼**|每個元素右邊「第一個比它大」的人是誰|當前窗口範圍內「所有人之中最大」的是誰|
|**尾端淘汰的意義**|棧頂元素終於等到了它的答案（新元素），結算並離開|隊尾元素「又舊又小」，在它過期前永遠不可能成為窗口最大值，提前淘汰|
|**頭部／底部會離開嗎**|**不會**。底部的最大值如果一直沒遇到更大的數，就一直留在棧底等待|**會**。隊頭永遠是當前最大值，但只要窗口往右滑動超出範圍，就必須從隊頭踢出|

### 為什麼單調棧解不了滑動窗口？

想像陣列 `[9, 5, 3, 2, 1]`，窗口大小 `k = 3`：

1. **在「下一個更大元素」中**：`9` 進棧後，後面的 `5, 3, 2, 1` 因為都比前面小，會依序疊在 `9` 上面形成 `[9, 5, 3, 2, 1]`。就算陣列有十萬個遞減數字，`9` 依然安穩地待在棧底，因為我們不限制距離，只要未來某天出現 `10`，就能一路把他們全部結算。
    
2. **在「滑動窗口最大值」中**：當窗口從 `[9, 5, 3]` 往右滑動到 `[5, 3, 2]` 時，最大的 `9` 已經**不在窗口裡了**。此時答案必須變成 `5`。如果我們用的是 `stack`，最大值 `9` 被壓在最底下拿不出來也刪不掉；改用 `deque`，就能直接檢查 `dq.front()` 的索引是否小於窗口左邊界，並透過 `pop_front()` 讓 `9` 退役，讓第二大的 `5` 順利補位成為新的隊頭。
    

> **一句話記憶法**：兩者都在**隊尾（棧頂）**淘汰「既老又弱」的冗員；但單調隊列還要在**隊頭**淘汰「德高望重但已退休（滑出窗口）」的元老。
